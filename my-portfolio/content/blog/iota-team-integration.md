## 先講結論

- **系統能動的那條主線很短**：App 送出開鎖 → API 寫資料庫並發布 MQTT → 橋接程式翻譯 topic → ESP32 轉動伺服馬達。真正難的不是任何一段，而是段與段之間的**接縫**。
- **接縫裡最危險的是「樂觀的成功」**：API 回「已發布」不代表門開了。這次碰到的大部分問題，都是某一段默默把東西丟掉，而上一段以為成功。
- **文件就是團隊之間的合約**：UC 文件、MQTT topic 表、HANDOVER 交接文件，讓不同人負責的 repo 能對齊。但文件沒有人維護就會和程式漂移，這也是我花最多時間的地方。

## 系統長什麼樣子

```text
 Flutter App ──HTTP :8091──▶ API gateway（FastAPI，每個請求跑一支腳本）
                                  │ 寫入
                                  ▼
                             MySQL（13 張表）
                    ┌─────────────┴──────────────┐
          發布 MQTT │                            │ ledger_events（待上鏈佇列）
                    ▼                            ▼
   home/{family}/device/{id}/cmd          Ledger Worker（樹莓派）
                    │                            │ 雜湊錨定
           topic 橋接程式                         ▼
                    │                  私有 IOTA Tangle（3 個 IRI 節點 + Compass）
                    ▼
     home/device/<mac>/cmd ──MQTT TLS :8883──▶ ESP32-S3 門鎖
```

後端由 7 個 Docker 服務組成：

| 服務 | 埠 | 做什麼 |
|---|---|---|
| mqtt-broker（Mosquitto） | 8883（TLS） | 所有裝置訊息的中樞，明碼 1883 已關閉 |
| mqtt-server | 8080 | 裝置註冊、下發設定、提供 OTA 韌體下載 |
| mqtt-monitor | 8090 | 網頁版的 MQTT 訊息監看，除錯用 |
| node-red | 1880 | 流程編排 |
| mysql | 3306 | 業務資料、稽核紀錄、待上鏈佇列 |
| api | 8091 | App 呼叫的 HTTP 入口，14 個路由 |
| api-mqtt-bridge | — | API 與韌體之間的 topic 翻譯 |

## 一個開鎖指令的旅程

1. **App**：使用者按下開鎖，App 把請求包成 `{"payload": {...}}` 送到 `control_device`，等待上限 25 秒。
2. **API**：檢查這個人在這個家庭的角色是否能操作裝置，寫入稽核紀錄，再發布到 `home/{family_id}/device/{device_id}/cmd`。
3. **橋接程式**：把 API 的 topic 翻譯成韌體看得懂的 `home/device/<mac>/cmd`，動作翻成 `unlock`。
4. **ESP32**：轉動伺服馬達，5 秒後自動上鎖，並把 `{"locked": false}` 回報到 `state`。
5. **回程**：橋接程式把狀態交給 API 的狀態更新模組寫回資料庫，App 再主動查詢最新狀態並更新畫面（App 沒有推播，只能輪詢）。

裝置這一側的 MQTT 協定如下，這張表也是 API、韌體、App 三方對齊時共同參照的版本：

| Topic | 方向 | 內容 |
|---|---|---|
| `home/register` | 裝置 → 伺服器 | 型號與 MAC，開機時送一次 |
| `home/device/<mac>/config` | 伺服器 → 裝置（retained） | 型號設定，例如 `auto_lock_sec` |
| `home/device/<mac>/cmd` | 伺服器 → 裝置 | `unlock`、`lock`、`doorbell_ack` |
| `home/device/<mac>/state` | 裝置 → 伺服器 | `{"locked": true/false}` |
| `home/device/<mac>/event` | 裝置 → 伺服器 | `doorbell`、`tamper_detected` |
| `home/device/<mac>/ota` | 伺服器 → 裝置 | 韌體網址、版本與簽章 |

## 上鏈：為什麼不讓 App 等區塊鏈

區塊鏈確認需要時間，IOTA 節點也可能暫時連不上。如果每個操作都等鏈上確認，App 會跟著卡住。所以系統採用「**待上鏈佇列**」：

1. API 在**同一個 MySQL transaction** 裡更新業務資料、寫稽核紀錄，並新增一筆 `ledger_events`，狀態是 `PENDING`。
2. commit 之後立刻回應 App，使用者不用等鏈。
3. 樹莓派上的 Ledger Worker 透過橋接 API 認領待處理事件（有租約時間，避免兩個 worker 搶同一筆），核對雜湊後提交到 Tangle。
4. 確認後回寫狀態；失敗最多重試 5 次，之後轉進 `DEAD_LETTER` 等人處理。重送前會先查鏈上是否已經有這筆，**不會盲目重複提交**。

上鏈的不是整筆資料，而是**雜湊錨定**：

- 事件內容先轉成固定格式的 JSON（鍵排序、固定分隔符），再算 SHA-256。
- 身分欄位在事件裡就只存雜湊；明文密碼、權杖、私鑰一律不進事件。
- 寫上鏈的錨定紀錄（事件 ID 加雜湊）再用每個家庭各自的金鑰做 AES-256-GCM 加密，存到加鹽雜湊過的家庭位址，家庭之間互相看不到。

會上鏈的是安全相關的關鍵事件：

| 使用案例 | 事件 |
|---|---|
| UC1.3 | 第一位管理者綁定閘道（整條鏈的起點） |
| UC2.1 | 裝置配對完成（ECDH 金鑰交換） |
| UC2.3 | 裝置除役、撤銷憑證 |
| UC3.3 | 撤銷家庭成員權限 |
| UC3.4／UC3.5 | 發出／撤銷訪客權杖 |
| UC4.4 | 安全異常（只限 8 種白名單類型） |

竄改示範的做法是：直接改資料庫裡的事件內容，連同它自己的雜湊一起改，看起來完全一致；但和鏈上的錨定一比對就會被抓出來。這正是把雜湊錨定在別人改不了的地方的意義。

私有 Tangle 跑在一台 Raspberry Pi 5（8 GB）上：3 個 IRI 1.8.6 節點加一個 Compass 協調器。記憶體大約 Compass 700 MB、每個節點 165–200 MB；三個節點的 milestone 一致（實測 67／67／67）。

> 我另外做過一個個人 PoC（[iota-project](https://github.com/chunhao0613/iota-project)），走的是另一條路：把一批異常資料做成 Merkle Tree，只把樹根錨定到 Shimmer 網路，驗證時用 Merkle proof 證明單筆資料屬於那一批。兩種做法的取捨是：批次省下上鏈次數，但要等批次送出才有證明；逐筆錨定每一筆都能單獨查證，成本隨事件數成長。專題採用的是逐筆錨定加待上鏈佇列，以門鎖這類事件量不大的系統來說，逐筆的成本可以接受。
>
> 那個 PoC 裡也有一個「4 條鏈比較」的頁面，但要誠實說明：只有 IOTA 真的送出交易，其他三條鏈只讀取 gas 價格，再用公式和固定幣價**估算**手續費。它是成本估算，不是實測的效能比較。

## 整合時踩到的接縫

### 1. 三套互不相容的 topic 命名

整合時才發現，程式裡同時存在三種 MQTT topic 慣例：

- 韌體與 mqtt-server 用 `home/device/<mac>/...`，這是**唯一接過真實 ESP32 的**。
- API 的開鎖程式用 `home/{family_id}/device/{device_id}/...`，從沒接過真裝置。
- 成員異動的通知發到 `home/security/gateway_{family_id}/auth_sync`，**沒有任何程式訂閱**，等於通知從沒送達任何人。

**決策**：以實測過的韌體慣例為準，另寫一支橋接程式做雙向翻譯，而不是回頭改 API。改 API 不會讓韌體多認得什麼，反而會讓兩套沒被驗證過的程式更難各自追蹤。

翻譯時還有一個小陷阱：`unlock` 這個字串本身就包含 `lock`。韌體如果先判斷 `lock`，開鎖指令會被當成上鎖，所以必須先判斷 `unlock`。

### 2. 「已發布」不等於門開了

App 連不上硬體時，我的判斷方式是先排除兩端：硬體單獨用指令測得動，App 也確實送出了請求，那問題就在中間。實際把中間這段攤開來看，有好幾個地方會**默默丟掉指令，卻讓上一段以為成功**：

- **只認得兩種動作**：API 支援 9 種動作，但韌體和橋接程式只認得 `LOCK`、`UNLOCK`。其他動作會在橋接程式被丟掉，只留一行 log，App 拿到的卻是「已發布」。
- **未配對的裝置**：狀態回報會被略過。
- **啟動順序**：伺服器在收到裝置的「註冊」時才開始接收它的訊息，所以必須**先啟動伺服器，再讓 ESP32 上電**。否則狀態與事件會被忽略。更麻煩的是，韌體斷線重連時不會重新註冊；伺服器如果中途重啟、但 ESP32 沒有重開機，就會一直收不到它的狀態。

排查這類問題的原則是**沿著鏈一段一段看訊息有沒有到**：MQTT 監看面板（`:8090`）、`mosquitto_sub` 訂閱 topic、資料庫的稽核紀錄，各自確認一段。只看 API 的回應，永遠只會看到「成功」。

### 3. 「剛回報的狀態顯示 8 小時前」

伺服器回傳的時間字串沒有帶時區，App 把它當成本地時間解析，結果台灣（UTC+8）的使用者看到剛剛的狀態寫著「8 小時前」。

修法是在 App 端統一規則：**收到沒有時區的時間一律視為 UTC，再轉成本地時間顯示；送給 API 的時間一律先轉成 UTC**，並補上測試。這個修正是我從 API 那邊的 App 原始碼同步到 App repo 的。

### 4. 規格和程式各走各的

文件是團隊之間的合約，但沒有人維護的文件會漂移。實際對照時找到的例子：

- **欄位名稱**：規格寫邀請人欄位叫 `inviter_uid`，程式用的是 `admin_uid`；規格寫回覆值是 `"Accepted"`，程式收的是 `Accept`／`Reject`。
- **回應格式**：大部分 API 回傳 `msg`，有兩支回傳 `message`，App 只好兩個都接。
- **端點不存在**：App 會呼叫 5 個在 API 主線上找不到的端點（建立家庭、列出家庭成員、查詢指令狀態等）。App 的原始碼在 API repo 的另一個分支開發，主線上的 API 沒有跟上。
- **區塊鏈對接文件**：最早規劃的 `/internal/ledger/events/*` 端點從沒實作，實際上做的是 `/ledger/*` 這組橋接 API。

最後一項是我直接處理的：在修正 Ledger Worker 的同時，把 9 份使用案例文件改成和實際實作一致，並明確標註舊端點「沒有實作」。

### 5. 硬體的雜訊會永久寫進稽核鏈

換到 ESP32-S3 之後，觸控感測器剛開機時會回傳未校準的巨大數值（實測開機瞬間 285402，穩定後只有 26734）。韌體開機 160 毫秒就取樣當基準，之後每次讀值都被判定成「有人在摸」，一次就往稽核紀錄灌了 **600 多筆假的門鈴與破壞事件**。

韌體的修法是先空轉 1.2 秒丟掉暖機讀值，取樣到 16 次波動小於 10% 才採用；同一支腳持續觸發超過 10 秒就重新校準。

但真正的教訓在後面：稽核紀錄是一條雜湊鏈，**這 614 筆假紀錄刪掉就會斷鏈**，只能留著。只能附加、不能修改的紀錄，寫入前的驗證就是唯一的防線。

### 6. 區塊鏈節點的維運比想像中脆弱

- **停機時間不夠**：`docker stop` 預設只給 10 秒，Compass 收尾需要 30 秒，每次停機都被強制終止，milestone 就停在 83、138 不再前進。修法是設定 60 秒的停機寬限期，並寫好有順序的啟動與停止腳本。
- **斷電**：曾經一次斷電讓整條鏈卡死，後來把恢復流程寫成操作手冊。
- **交易一直停在待確認**：原因是 bundle hash 沒有正確計算，送出去的全是 `"9" × 81`。我改用標準函式庫自己實作 Kerl 雜湊，並改用 milestone 確認交易狀態。這個修正當時還沒在真實節點上完整驗證，我在進度文件裡註明了。

## 還沒做完、我會優先補的地方

照風險排序：

1. **API 走明碼 HTTP，而且登入不發權杖**：App 的密碼是明碼送出的（伺服器端有用 bcrypt 雜湊儲存），身分只靠請求裡的 `user_id`。這是最優先的缺口：API 要加 TLS，登入後要發有效期限的權杖，每個請求都要驗證。
2. **MQTT 沒有身分驗證**：TLS 只保證傳輸加密，不代表對方是誰，兩者是不同層次。broker 目前允許匿名連線，下一步要做每台裝置一組的帳號或用戶端憑證。
3. **還沒在真實硬體上驗證的**：觸控事件、ESP32 上的 TLS 與對時、真機 OTA。OTA 韌體已經加上 Ed25519 簽章（伺服器端用假韌體驗證過），設計上即使下載走 HTTP，被換掉的韌體也會被拒絕；但這要等真機驗證過才算數。
4. **未完成的使用案例**：緊急實體開鎖的離線同步（UC4.5）、撤銷訪客權杖（UC3.5）。
5. **還連在明碼 1883 的元件**：Node-RED 與告警服務在改成 TLS 之後沒有跟著更新。

## 重來一次我會怎麼做

- **切成四層、每層一位負責人**：前端、後端、硬體、IOTA。這次的分工是 App、API、硬體、IOTA、資料庫五塊，但實際投入的人不多，資料庫和 API 的邊界又模糊，接縫反而沒人顧。
- **把接縫寫成可以自動檢查的合約**：MQTT topic 表、API 欄位、上鏈事件格式，各有一份唯一的定義檔。CI 裡至少檢查「App 呼叫的端點都存在於 API 路由表」，第 4 節的問題就不會等到整合才發現。
- **回應要誠實**：API 不應該回「已發布」就結束，而是回傳指令編號，讓 App 查到裝置真正的回報為止。
- **人力集中在專題重點**：IOTA 是這個專題的核心，但樹莓派上的私有 Tangle 和 Ledger Worker 到 10 月中才跑通，是最晚完成的一塊。應該一開始就投入最多人，讓上鏈流程最早跑通。
