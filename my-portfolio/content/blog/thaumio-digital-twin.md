## 問題：測 IoT 後端，卻沒有裝置

做智慧家居專題時，後端、App、資料庫的進度常常要等硬體。裝置數量有限、只能由負責硬體的人操作，想測「一百台裝置同時回報」或「某台裝置突然異常」幾乎不可能。

這不是只有我們會遇到的問題。所以我決定不只做給專題用，而是做成**任何軟硬體開發者都能用的開源工具**。

**目標使用者**：需要測試 IoT 後端、資料平台或異常偵測模型，但手上缺乏硬體設備的開發者。

## 最重要的決定：先不做 3D

我一開始想做的是視覺化的數位雙生，能看到裝置和環境的 3D 畫面。但越想越發現它和「好用的測試工具」互相衝突：

| 方向 | 好處 | 代價 |
|---|---|---|
| 3D 視覺化 | 直觀，適合展示與教學 | 很重、要 GPU，放不進 CI |
| 資料與行為層 | 輕量、Docker 一行就跑、適合自動化測試 | 看不到畫面 |

我選了**輕量**。數位雙生通常分成三層：外觀幾何、物理力學、資料行為。Thaumio 只做第三層，前兩層明確標成「不做」。

3D 沒有被放棄，只是延後。我仍考慮之後把它發展成**教學或模擬用途**的獨立方向，而不是塞進測試工具裡讓它變重。

## AI 提出、我採用的：用 JSON 宣告整個拓撲

「用一份 JSON 描述環境、閘道、協定、裝置和狀態公式」這個做法是 AI 提出的。我評估後採用，原因是它符合「輕量、可放進版本控制、可自動化」的定位。

採用之後也帶出新問題：JSON 物件的 key 沒有順序，公式 A 如果依賴公式 B，被格式化工具重新排序後就可能失敗。最後的解法是**雙緩衝狀態求值**：每個 tick 都只讀上一輪的狀態快照、算完再一次寫回，結果就不受 key 順序影響。另外附上 JSON Schema，讓設定檔在 VS Code 裡就能自動補完和檢查錯誤。

> 我想誠實標出哪些點子是誰的。AI 很擅長提出方案，我的工作是判斷它符不符合產品的定位，並追問它帶來的後續問題。

## 現在能做什麼

- **一份設定檔就能啟動**：宣告式拓撲加上 Schema 驗證
- **連續狀態模擬**：電池充放電、水位這類會隨時間累積的狀態
- **混沌注入**：透過 API 模擬颱風、日蝕等突發狀況，結束後回到原本的物理模擬，不殘留影響
- **常見的輸出管道**：CSV／JSONL／SQLite、HTTP、MQTT（含 mTLS）、Kafka、AWS IoT、Azure IoT Hub、GCP Pub/Sub、InfluxDB
- **兩種跑法**：本機 CLI，或 Docker 容器加 Swagger 控制介面

在 IOTA 專題中，我們就用 Thaumio 產生裝置資料，去比較 4 條區塊鏈的上鏈效能。

## 我從這個專案學到的

1. **定位要先講清楚「不做什麼」。** 把 3D 拿掉之後，每個技術選擇都有了判斷標準：會不會讓它變重？
2. **AI 的提案要追問後果。** JSON 宣告很好，但 key 順序的問題要等你追問才會浮現。
3. **從自己的痛點出發，再想別人能不能用。** 這讓工具一開始就有真實的使用情境。
